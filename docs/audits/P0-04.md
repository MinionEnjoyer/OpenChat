**Earlier observed clean runs:** The initial baseline run (before mutation probes) confirmed 84/84 at 3.247s. From the terminal session history, the implementing agent's runs also show 84/84 with complete stack restarts.

**Timing variance:** Runs 1–3: 4.387s, 3.965s, 3.932s (after warm-up, variance within ~10%).

**Verdict:** PASS with caveat — contaminated by audit artifacts. The implementing agent's claim is credible but I did not obtain independent 3×84/84 due to test state leakage from probe mutations.

### Determinism concerns

**Fixed sleeps and waits (grep of suite):**

| Location | Wait | Type |
|----------|------|------|
| `global-setup.ts:27` | `setTimeout(r, 1000)` in health-check retry loop | Poll-with-retry (up to 30 attempts). Acceptable. |
| `helpers.ts:100–101` | `setTimeout(…, 10_000)` connection timeout + `setTimeout(check, 100)` polling loop for `ready` frame | Poll-with-timeout. Acceptable. |
| `ws.spec.ts:44` | `await new Promise(r => setTimeout(r, 300))` after subscribe | **Fixed wait.** Not polling. If subscribe acknowledgement takes >300ms, test will flake. |
| `ws.spec.ts:58` | `await new Promise(r => setTimeout(r, 300))` after unsubscribe | Fixed wait. |
| `ws.spec.ts:60` | `await new Promise(r => setTimeout(r, 300))` after second subscribe in message.send test | Fixed wait. |
| `ws.spec.ts:64` | `await new Promise(r => setTimeout(r, 500))` after post-unsub | Fixed wait. |
| `ws.spec.ts:76` | `await new Promise(r => setTimeout(r, 300))` in message.send test | Fixed wait. |

**DRIFT.** WS tests use fixed waits (300–500ms) rather than polling-with-timeout. These will flake under CI load or on slower machines. The characterization task spec (02 §P0-04) doesn't explicitly mandate polling, but `05-AGENT-OPERATIONS.md §3` prohibits "retrying a flaky flow >2× without opening a DL" — these fixed waits make flakes more likely.

**Inter-test coupling via shared seed state:**

- All tests in a file use `beforeAll(async () => { s = await seed(); })` — one seed per file. Tests within a file share mutable state.
- `pins-polls.spec.ts:14`: `await apiFetch(\`/messages/${s.messageIds[0]}/pin\`, …)` — unpins a seed message that was never pinned. If a prior test pinned it, the result would differ.
- `dms-friends.spec.ts:39`: `if (pending.body.length > 0)` — conditional on prior test behavior (friend request may or may not exist).
- `roles.spec.ts:40`: `expect(res.status).toBeLessThan(500)` — accepts any 2xx/3xx/4xx, so inter-test variation is masked.

**Sequential-only config** (`jest-char.config.js:13` `maxWorkers: 1`) hides these couplings but doesn't eliminate them. **DRIFT** — a partial rerun (`--testNamePattern`) could behave differently than a full suite run.
